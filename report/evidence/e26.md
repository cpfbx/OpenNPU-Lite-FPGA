# 2026-09-11 C-store writeback pipeline experiment

## Hypothesis

For a full 64×64×64 Tile, the existing core spends roughly three cycles per 4×4 result element on C-store read/modify/write. A one-read/one-write-per-cycle pipeline could reduce each microtile writeback from about 48 cycles to 17 and materially improve compute-accounted throughput.

## Experiment

The C store kept one syntactic read port while the state machine issued one address per cycle and wrote the previous read result through a separate write path. All 15 RTL testbenches and all 4,196 checks passed, so the arithmetic and protocol behavior were functionally sound. Out-of-context synthesis met 100 MHz with WNS `+1.806 ns`.

## Rejection reason

Vivado 2026.1 reported `ram_style="block"` as infeasible for this inferred read/write pattern and mapped the 4096×32 C store to 1,408 RAM64M primitives instead of four RAMB36E1 blocks. That would recreate the resource failure already removed from the full overlay. Timing improvement alone therefore did not satisfy the resource gate.

The experiment was reverted before any full-overlay build or board programming. A clean synthesis of the restored Build `0x20260911` source again inferred exactly four RAMB36E1 blocks and reproduced OOC WNS `+1.072 ns`.

## Follow-up decision

Do not retry the same inference template. A future writeback pipeline must use either an explicit simple-dual-port XPM/BRAM wrapper with collision behavior defined and verified, or a changed accumulation architecture. It remains secondary to the already stable BRAM baseline.
