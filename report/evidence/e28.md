## 3. Useful practices, and their limits

### 3.1 Ultra-Vision: explain data movement before listing optimizations

Its two designs retain the algorithm but change DDR/FIFO placement and output buffering. The README explains the bandwidth/timing conflict and frame-size synchronization tradeoff, rather than treating ping-pong buffering as an automatic improvement. It also puts architecture, hardware photos and demonstration entry points near the front. [Repository explanation](https://github.com/Floatkyun/Ultra-Vision/blob/9b3f664d2f9df09b945adcd36c6ca69e09025820/README.md).

For OpenNPU: explain why K-major layout, first-K overwrite, prefetch and dual C-Bank overlap remove specific work or stalls; then show measured results for the corresponding BIT identity. Do not add historical savings or multiply their speedups. For host optimization, investigate actual packing/copy/object work before proposing another DMA batching layer that already exists. Do not adopt the reference project's qualitative latency claims as an independently verified metric.

### 3.2 ANLU: build a demonstrable system in stages

The repository exposes incremental control/data/image integration, setup assumptions and an explicit host-side receive path. The selected receiver uses frame/packet identifiers, bounded queuing and stale partial-frame handling. These are concrete integration mechanisms, not proof of general packet-loss tolerance or real-time guarantees. [Project and host source](https://github.com/maojinxiang/FPGA-ANLU-National-First-Prize/tree/df3b509b201a8f4103114d7dc8d78dd16193b10b).

For OpenNPU: a short entry point should show the input identity, selected backend, exact comparison, timing scope and final cleanup/status. Reuse current receipts and logs; no new GUI platform is justified merely for presentation. Demonstrate the matrix service first. Present KWS as a scoped application integration/rejection example unless further approved evidence changes that boundary.

### 3.3 PYNQ-Z2 UKF: connect the kernel to an application, and audit the instructions

The project separates software and hardware notebook routes and includes a MATLAB-reference comparison and scripted HLS flow. This is useful for explaining what PS does, what PL does, and which reproduction route needs a board/toolchain. Its numerical tolerances are application-specific and must not replace our exact INT32 oracle.

There is also a reproducibility warning at the pinned snapshot: README text describes default `CSIM=1`, `CSYNTH=0`, `COSIM=0`, whereas the actual Tcl starts with all of `CSIM`, `CSYNTH`, `COSIM`, `VIVADO_SYN`, `VIVADO_IMPL` set to 1. See the [README](https://github.com/hongpengWu/hlstrack2025_40562/blob/264bb94cab8b7e10d7874b9b91d28b50f730d8c1/README.md) and [Tcl](https://github.com/hongpengWu/hlstrack2025_40562/blob/264bb94cab8b7e10d7874b9b91d28b50f730d8c1/yolo_ukf_track/src/kernel/run_hls.tcl#L3). No script was executed here. An award claim does not remove the need to verify actual execution flags.

Ultra-Vision reports MIT and the UKF repository Apache-2.0, with third-party attributions also requiring attention. No explicit root license was found for the ANLU repository in this inspection (GitHub API license was null); this is an unresolved reuse boundary, not permission to copy. No third-party code, image or poster was imported into OpenNPU. Ideas can inform our independently produced explanation, with attribution.

## 4. Recommendations for our next steps

These are proposed priorities, not authorization for new board work or publication.

1. **Finish the real matrix off-machine reproduction handoff first.** V's separate-computer AI-assisted Skill exercise is useful usage evidence, but is not the matrix package's 191-test reproduction. Keep the two records separate. Provide fixed hashes, environment requirements, commands, exit-code collection and a post-test identity check. Separate PC verification, source rebuild, board functionality and controlled measurement as four different levels.
2. **Make the contribution legible.** Present a reproducible INT8 compute platform, measured dataflow/host tradeoffs and reusable validation practices. The core claim is not a universally faster/lower-energy replacement for dual-core ARM. Retain the bounded source-diagnostic window rather than launching an unproved rewrite.
3. **Produce a small set of evidence-backed figures.** PS/PL dataflow and interface; hardware evolution with distinct BIT identities; a nested timing diagram with unassigned overhead retained; same-session backend comparison; nominal ABBA envelope power/time/energy. A DMA+PL subwindow must not be added twice or compared with a CPU complete request as an end-to-end speedup.
4. **Make the demo short and truthful.** Existing golden inputs, exact outputs, conservation counters and lifecycle status are the primary engineering demonstration. The one live KWS misclassification rejected by the gate is one rejection case, not successful classification or a deployment-quality evaluation. No extra run or relaxed threshold is implied by this proposal.
5. **Create a derived submission tree only after decisions.** Map guide requirements to the final source/build/board/data/skill/report material; distinguish current candidates from frozen historical packages. Resolve naming, third-party/IP/model licensing, private-path redaction and the real poster template before public export. Preserve all frozen originals.

## 5. Current gaps this study does not close

- No independent performance reproduction of these reference repositories, no exhaustive review and no causal proof of why judges awarded them.
- No confirmation of our registration group, latest submission-portal changes or canonical-uppercase filename exception.
- No new matrix optimization result, calibrated task-energy result, KWS accuracy improvement, cross-board Skill reuse or matrix off-machine test receipt.
- No change to the measured conclusion: our FPGA saved-envelope mean power was lower than ARM 2t, but its measured nominal envelope duration and cumulative joules were higher. This is not repaired by changing presentation.
- No score or award guarantee. The useful lesson is to pair a focused engineering contribution with understandable architecture, real comparisons and an executable reproduction path.
